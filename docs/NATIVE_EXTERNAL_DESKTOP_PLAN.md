# 原生外接桌面接通与兼容性修复计划

日期：2026-11-10（北京时间）

状态：用户已接受方向。本文末尾保留建档时的状态；执行进度与接续工作见 [PROGRESS.md](PROGRESS.md) 和 [HANDOFF.md](HANDOFF.md)。

研究基线：`a1cab8a`，popsicle / `OS4.0.6.0.XPBCNXM` / Android 17 / SDK 37。

## 1. 目标与范围

在现有 HyperOS 组件基础上，研究并接通原生外接桌面，处理它与小米窗口管理体系的兼容问题。

- 不依赖 SmartDock、Taskbar 或其他第三方桌面应用，不替换手机主桌面。
- 优先复用 MiuiHome 的次屏 HOME、SystemUI、WM Shell 及现有 MIUI 窗口能力。
- 手机内屏和背屏继续正常工作；保持原有安全、可信显示及背屏访问限制。
- 必要的可逆模块只承担配置、策略修正、控制和诊断，不成为新的桌面实现。
- 原生独立桌面、窗口管理、正确尺寸和物理高刷分别研究、分别验收。

本计划调整了 [05 实施方案比较](../reports/05-implementation-options.md) 的后续优先级：独立第三方桌面不再作为目标或自动回退方案；全局关闭设备限制不作为默认实验。旧报告仍保留为首轮研究记录。

创建本计划不等于开始执行设备操作。现阶段只建立文档；后续离线研究与未来设备验证分别记录。原任务明确要求不执行真机操作，阶段 4 及以后的设备采集、修改、安装、Hook 或重启，必须在另行明确授权范围后开展。

## 2. 计划依据与证据边界

### 2.1 当前 ROM

七个目标分区已通过 payload manifest 哈希校验并完成 EROFS 提取；已有 97 个 packaged Overlay 扫描结果和 24 组方法定位。继续使用既有输出，不从头重复解包。

已定位的事实：

- Framework 基础桌面资格资源为 false；原生桌面、投射桌面和内容模式管理相关核心 flag 为 true。
- `DesktopModeHelper`、`DesktopStateImpl` 及组件创建方法具有资格判断；部分结果在初始化时缓存。
- `SecondaryDisplayPolicy` 可把关闭的镜像设置恢复为开启。
- MiuiHome 声明 `SecondaryDisplayLauncher`；其 APK 无常规 DEX，包含原生代码载体，具体次屏行为尚未恢复。
- `DesktopStateImpl` 位于独立 `Miui-WindowManager-Shell.jar`；不能只扫描 MiuiSystemUI APK 推断实现是否存在。
- 背屏 ID 1 有专用处理，不能将全部非 0 显示器当成外接屏。
- 已追踪条件性的 priority 24 全局 0–60 RenderVote 及下游模式筛选；物理输出上限尚未确认。

证据入口：[ROM 信息](../reports/01-rom-information.md)、[HyperOS 限制](../reports/03-hyperos-restrictions.md)、[刷新率研究](../reports/04-display-refresh-rate.md)、[方法定位清单](../analysis/evidence/findings.json)。

### 2.2 小米官方解释

小米《Android 16 应用适配指南》§2.11 说明：工作台模式、无极窗口提供类似能力，为“避免功能冲突”屏蔽 Google 原生桌面窗口模式，并建议开发者适配小米方案。

这为调查双窗口体系的兼容关系提供依据；该说明针对 Android 16，不能单独证明本机 Android 17 每个限制的原因，也不能证明手机外屏已有等效替代。

- [官方 Android 16 应用适配指南](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=2035)
- [官方工作台模式适配指南](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=2034)

### 2.3 HyperDesktopUnlock 对照

固定对照提交：[`ee0c3d4d3abee7ab0f5a88f92cf82edb260ac948`](https://github.com/the-marox/HyperDesktopUnlock/tree/ee0c3d4d3abee7ab0f5a88f92cf82edb260ac948)。后续若参考新版本，另记提交和差异。

可借鉴：恢复系统外屏连接入口、连接选择处理、镜像恢复策略的观测与修正、显示生命周期和诊断方式。

必须重新适配或排除：

- 第三方 Dock 启动、Dock 无障碍管理、自绘任务切换浮层不进入首轮原生目标。
- 按非 0 displayId 放行的逻辑，改为核对真实外接物理显示，保留内屏、背屏、私有/不可信和虚拟显示的限制。
- 仅遍历进程 APK 寻找接口实现的逻辑，不能覆盖本 ROM 共享 JAR 中的实现；需核对类加载器、具体类和加载时机。
- 作者记录过强制全局资格或关闭设备限制后的稳定性问题；这些是他机/他版经验，不能写成本机已复现，但足以要求避免直接照搬。
- 项目可选的 `SecondaryHomeHooks` 会屏蔽原生次屏 HOME；本计划保留该 HOME 的研究与复用，不默认启用屏蔽。
- 不默认采用手机自动熄屏、触摸板、IME 重定向及密度/尺寸调整等附加功能。

项目 README 或源码注释中的机型测试、成功与失败均按外部报告处理，不作为独立的本机验证结果。复用开源实现时保留相应许可与来源。

## 3. 实现路线与决策顺序

先确认窗口由谁管理，再确定需要修正的最小条件。

| 路线 | 组成 | 选择所需证据 |
|---|---|---|
| A：优先评估 | MiuiHome 次屏入口 + 现有 MIUI 窗口管理 | 次屏能承载任务；厂商管理器在外屏的作用范围、依赖及恢复行为明确 |
| B：候选 | MiuiHome 次屏入口 + 适用于外屏的 AOSP WM Shell 桌面组件 | AOSP 组件依赖可满足；与 MIUI 处理同一任务的冲突可避免或修复 |

不预设两套管理器可以简单按 Display 拆分，也不同时把两套全局能力全部启用。单一资格开关没有显示参数时，不得声称修改只影响外屏。

如果原生入口或窗口能力不足，记录缺项、阻断点和证据；不自动引入第三方桌面，也不以自绘桌面界面替代原生目标后宣布完成。

## 4. 分阶段执行计划

### 阶段 1：统一证据和剩余问题（离线）

工作：

- 复用现有 ROM、AOSP 固定提交与方法证据，纳入官方解释及固定版本项目对照。
- 建立“能力—入口—消费者—限制条件—作用显示—缓存/初始化—副作用—验证方式”矩阵。
- 区分 AOSP 默认值、已确认的厂商差异、外部项目报告、推测和运行时未知项。
- 将原生独立输出、次屏 HOME、任务管理、自由窗口、尺寸和物理高刷分开编号。

产物：证据矩阵、待解决问题清单、上游移植对照表。

通过条件：每个候选改动有具体资源/方法、输入条件和影响范围；证据能定位至 ROM 文件哈希或固定源码提交。

### 阶段 2：补齐原生桌面与窗口链路（离线，优先级最高）

工作：

- 从 manifest、原生库、运行时注册/加载线索追踪 `SecondaryDisplayLauncher`，恢复能复查的生命周期和应用启动路径。
- 检查次屏与主桌面是否共享进程、资源或手势状态，追踪 display context、配置/密度变化的传播范围。
- 补齐 `DesktopStateImpl`、WM Shell 依赖创建、任务组织器、系统装饰和 HOME 启动的调用关系。
- 分析 MIUI 与 AOSP 窗口组件是否共同处理同一任务，以及尺寸、焦点、动画和 Insets 的职责。
- 跟进 `ExternalScreenCompatPolicy` / controller 配置，区分应用缩放与镜像 viewport、物理模式。

产物：“外屏连接 → 内容模式 → 次屏 HOME → 应用任务 → 窗口管理”调用图、双窗口体系职责表、原生逆向未恢复项清单。

通过条件：能说明各组件由谁创建、何时执行、对哪个显示生效。无法恢复的方法保留为未知，不用字符串或失真的反编译代码填补调用图。

停止进入实现的条件：任务组织器归属、初始化顺序或主次屏配置传播仍不明确；继续离线分析，不直接强制放行。

### 阶段 3：选择路线并设计最小改动（离线）

工作：

- 根据阶段 2 证据选择路线 A 或 B，记录理由、缺项和不采用另一条路线的原因。
- 对恢复系统入口、资格、镜像策略逐项分析；优先已有配置，确认配置不可用后再评估限定的低频 Hook。
- 把诊断观测与行为修改分开；设计版本/哈希门控、默认关闭、独立关闭入口和有界日志。
- 明确跨进程资格是否一致、已缓存状态如何重建、单个变更的恢复方式。
- 将“只读观测”“最小修改”“扩展功能”拆开，不将高刷、尺寸调整与桌面解锁同时打包测试。

产物：最小补丁设计、类/方法/类加载器兼容表、预期状态变化表、恢复与实验说明。

通过条件：选定路线、具体改动、影响范围、初始化依赖和恢复路径完整；未知 KernelSU 版本/模块能力作为设备阶段前置条件，不假设其他 Root 方案的工具必然存在。

本阶段不安装模块，不调用 Hook，不写设备属性或 Settings，不把离线可构建等同于设备可运行。

### 阶段 4：真机只读基线（未来另行安排）

工作：

- 另行明确设备操作范围后，使用现有只读采集方案比较未接外屏与连接镜像状态。
- 核对 ROM 指纹、真实 EXTERNAL 物理显示、flags/content mode、HOME 解析、Overlay 和资格状态。
- 核对 Shell 实例化、系统装饰、任务承载、输入映射、渲染投票及物理显示模式。
- 确认 KernelSU Official 的实际版本、模块环境及可用恢复方式。

产物：带实验编号的基线日志、静态/运行时差异表、设备兼容与恢复记录。

通过条件：外屏识别可靠，关键静态推断已与设备状态对齐；缺失或权限拒绝保留原始证据，不自动升级成写操作。

相关脚本及命令见 [06 真机验证计划](../reports/06-device-validation-plan.md)。本计划建立时，该阶段仍为 NOT_RUN。

### 阶段 5：分步验证原生桌面（未来设备实验）

在原有物理模式、逻辑尺寸和密度下，按已确认的阻断条件安排单变量实验：

1. 优先使用现有系统应用验证外屏独立 Activity/task，核对内屏显示不同内容。
2. 验证系统原生次屏 HOME 的解析、创建和行为；若被拒绝，记录实际原因，不跳过判断直接启动完整补丁。
3. 按拒绝原因依次对照最小入口、资格或镜像策略修正。保留用户返回镜像的正常路径。
4. 验证原生应用启动、切换、关闭、焦点和拔屏任务恢复。
5. 接通所选窗口管理路线，分别验证窗口装饰、调整大小、最大化等已有原生能力。

若确需诊断探针，它仅显示/记录信息，不注册 HOME，不成为桌面运行依赖。新探针安装同样属于另行安排的设备实验。

产物：每个变更的前后日志、PASS/FAIL/PARTIAL 记录、恢复对照和缺项说明。

通过条件：外屏原生 HOME 与任务可用，内屏和背屏正常；只有独立应用画面、没有可用桌面时只能记为阶段性结果。原生独立桌面通过，不代表自由窗口已通过。

停止与恢复条件：内屏手势失效、持续卡顿、布局错位、SystemUI/system_server 崩溃、异常重启或无法返回基线。恢复当前变量并记录，不继续叠加下一组修改。

### 阶段 6：尺寸、黑边和物理高刷（单独验证）

工作：

- 桌面路径稳定后，分别检查镜像 viewport、应用兼容缩放、逻辑尺寸/密度及物理输出时序。
- 对齐 Framework RenderVote / mode 筛选、SF/HWC 活动模式、EDID/DRM modes 和显示器 OSD。
- 只选择硬件链路实际暴露且证据支持的模式，不虚构 120/180 Hz 时序。
- 完成 `hdmi_cfg_idx` 消费路径及参数格式分析前不猜值试写；不默认制作 HAL、内核或 DTBO 补丁。
- 同步观察内屏/背屏并发、热状态、功耗及输入，不关闭全部温控或 MIUI optimization。

产物：尺寸/缩放原因说明、模式对照表、60 限制的分层结论和高刷验证记录。

通过条件：正确尺寸与物理高刷分别有对应外接物理显示的证据。`wm size`、RenderVote 解除、逻辑屏显示 120 或虚拟屏刷新率都不能单独作为物理高刷 PASS。

### 阶段 7：回归、交接与交付

工作：

- 覆盖插拔、锁屏/唤醒、旋转、鼠标/键盘/手柄焦点、IME、内屏手势、背屏、重启及禁用恢复。
- 执行前记录测试次数、时长和预期；每次记录固件、显示链路、前置状态及实际结果。
- 分开结论：原生独立桌面、原生窗口管理、正确尺寸、物理高刷、输入、性能和恢复。
- 若形成模块，附已验证版本、依赖、开关、已知问题和与实际环境一致的恢复说明。

产物：回归报告、最终验收矩阵、可复现源码/构建说明及交接记录；仅在证据充分时交付测试模块或可用版本。

通过条件：所有承诺项均有结果；未实现或未验证项明确写出，不用第三方桌面替代后标记原生目标完成。

## 5. 执行约束

- 原始 ROM 和原始分区镜像保持只读，不刷机，不直接修改系统分区镜像。
- 不全局放行 Activity 显示校验，不绕过 REAR/private/trusted 等限制。
- 不 Hook 主 Launcher 的逐帧动画、绘制或高频布局路径；不同时启用未经协调的窗口管理器。
- 不默认关闭 `persist.wm.debug.desktop_mode_enforce_device_restrictions`，不把全局 helper 强制 true 当成首个实验。
- 持久属性、Settings 和 Overlay 保存原始状态；原来不存在的键按不存在恢复，不能只禁用模块而遗留状态。
- 确定某项必须真机后进入待验证清单，离线阶段继续推进不依赖该结果的工作。
- 反编译失败、缺少 native 符号或外部项目失败记录均保留边界，不编造调用关系和补丁效果。
